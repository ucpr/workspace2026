# atama 要件定義書

## 0. 文書情報

- 対象リポジトリ: atama
- バージョン: v0.1 (初版)
- 作成日: 2026-09-06
- ステータス: ドラフト（実装着手前レビュー用）

## 1. 背景・目的

AIエージェント（Claude Code, Codex 等）にソフトウェア開発タスクを委譲する機会が増えている一方で、以下の課題がある。

- タスクが Issue やチャット指示に散在し、エージェントが「次に何をすべきか」を機械的に判断できない。
- タスク間の依存関係（このタスクが終わらないと着手できない、等）を人手で管理しており、エージェントに順序立てて実行させにくい。
- GitHub Issues に情報が集約されているが、Issue 単体では依存関係やエージェント実行のための構造化データを表現しにくい。
- 人間がタスクの全体状況を素早く俯瞰・整理する手段がない。

本ツールは、**エージェントが CLI 経由でタスクを登録・参照・更新でき、依存関係に基づいて次に実行すべきタスクを機械的に決定できるタスク管理基盤**を提供する。あわせて、人間が TUI 上でボード形式にタスクを整理できるようにし、GitHub Issues との相互運用性を持たせることで、既存のワークフローに統合しやすくする。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| タスク (Task) | 管理対象の作業単位。GitHub Issue に相当する項目に加え、依存関係・実行メタデータを持つ。 |
| ゴール (Goal) | 1つ以上のタスクをまとめた達成目標。ゴール配下のタスクを依存関係順に実行することで達成される。 |
| 依存関係 (Dependency) | タスク A がタスク B の完了を前提とする関係（`B depends_on A`）。 |
| Ready タスク | 依存先タスクがすべて完了状態であり、着手可能なタスク。 |
| エージェント (Agent) | 本ツールを CLI 経由で操作し、タスクの実行を行う主体（人間、または Claude Code 等の外部プロセス）。 |
| 実行委譲 (Delegated Execution) | 本ツールはタスクの実行そのものは行わず、「次に実行すべきタスク」を提示するに留め、実際の実行は外部のエージェントプロセスが行うモデル。 |
| 実行フック (Executor Hook) | 将来拡張として、タスクごと/全体でコマンドを登録し、本ツールがそのコマンドを起動してタスクを自動実行できるようにする仕組み。 |
| ボード (Board) | TUI 上でタスクをステータス別（カンバン形式）に表示する画面。 |
| Sync | GitHub Issues とタスクデータ間の情報同期（インポート／エクスポート／双方向）。 |

## 3. スコープ

### 3.1 主眼とするスコープ（MVP）

- **個人・単一マシンでの利用**を前提とする。ローカルファイルシステム上でタスクデータを完結して管理する。
- 本ツールは **タスクの登録・依存関係管理・状態管理・次アクションの決定** を担い、**タスクの実際の実行（コード変更やコマンド実行）は行わない**（実行委譲モデル）。
- GitHub Issues との連携は **単一リポジトリ** を対象とする。
- CLI によるエージェント操作と、TUI によるボード表示・人手での整理の両方を提供する。

### 3.2 非スコープ（v0.1では対象外。将来拡張として設計上の余地は残す）

- 複数人・複数マシンでの共有利用（サーバー化、DB共有、権限管理、リアルタイム協調編集）。
- 複数 GitHub リポジトリを横断したタスク管理。
- 実行フック機構の具体実装（タスクを自動実行するランナー本体）。ただし **将来追加できるように拡張点は設計に含める**（§8.3）。
- GitHub Issues 以外の外部トラッカー（Jira, Linear 等）との連携。
- 通知（Slack/メール等）や高度な権限・監査ログ。

## 4. 想定利用シナリオ（ユースケース）

1. **エージェントによるタスク登録**: Claude Code がユーザーの指示を複数タスクに分解し、依存関係付きで CLI から登録する。
2. **エージェントによる自律実行ループ**: エージェントが `next` 相当のコマンドで実行可能なタスクを取得 → 実行 → 完了報告 → 次のタスク取得、を繰り返す。
3. **ゴール実行**: 人間またはエージェントが「このゴールを進めて」と `/goal` を実行し、ツールが依存順にタスクを1件ずつ提示する。
4. **人間による整理**: 開発者が TUI を開き、ボード上でタスクのステータスを移動したり、依存関係や優先度を調整する。
5. **既存 Issue の取り込み**: リポジトリの既存 Issue 群をインポートし、依存関係やゴールを付与してタスク化する。
6. **タスクの Issue 化**: ローカルで作成したタスクを GitHub Issue としてエクスポートし、チームに共有する。
7. **同期**: ローカルタスクと GitHub Issue の間で状態やコメントのずれを検知し、同期する。

## 5. 機能要件

### 5.1 タスク管理（CRUD）

- タスクの作成・参照・更新・削除ができること（CLI コマンド、詳細は §7）。
- タスクは一意な ID を持つ（内部 ID。GitHub Issue 番号とは独立）。
- タスクは以下の基本属性を持つ（詳細データモデルは §6）。
  - タイトル、本文（Markdown）、ステータス、ラベル、優先度、担当者（任意）、作成日時、更新日時。
- タスクのステータスは GitHub Issue の open/closed よりも粒度の細かいワークフロー状態を持つ（例: `backlog` / `ready` / `in_progress` / `blocked` / `in_review` / `done` / `cancelled`）。
  - `blocked` は依存未解決により自動的に判定される導出状態としても扱える（明示的な手動 `blocked` 設定とは区別する）。
- ステータス間の遷移に制約は設けない（自由遷移）。`done` から `in_progress` に戻す等も許可し、エージェント・人間の運用判断に委ねる。

### 5.2 依存関係管理

- タスク間に有向の依存関係（`depends_on`）を設定・解除できること。
- 依存関係は DAG（有向非巡回グラフ）であることを保証し、循環依存はコマンド実行時にエラーとして検出・拒否する。
- 与えられたタスク群（ゴール配下のタスク等）に対し、トポロジカルソートで実行順序を算出できること。
- ある時点で「Ready（依存がすべて完了 or 未設定）」なタスク一覧を取得できること。
- 依存先タスクが `cancelled` になった場合の扱い（後続タスクを自動的にブロックするか等）を設定可能にする（デフォルト: 警告を出し `blocked` 扱いにする）。

### 5.3 ゴールと `/goal` 実行フロー

- 複数タスクを束ねる「ゴール」を作成できる。ゴールは名前・説明・所属タスクのリストを持つ。
- `/goal <goal-id>` 相当のコマンドは、ゴール配下のタスクのうち Ready なものを依存順に提示する。
- 本ツールは **実行委譲モデル** を基本とする：
  - タスクを直接実行（シェルコマンド起動やエージェント呼び出し）はしない。
  - 「次に実行すべきタスク」を人間可読形式・機械可読形式（JSON）の両方で出力する。
  - 実行主体（エージェント）は取得したタスクを自分で処理し、完了後に本ツールへ完了報告（ステータス更新）を行う。
  - このやり取りをループするだけで、エージェントは自律的にゴールを進行できる。
- **拡張性の要件**: 将来的に「タスクごとに実行コマンド（実行フック）を登録し、本ツールがそれを起動して自動実行する」モードを追加できるよう、以下を設計時点で考慮する。
  - タスク/ゴール/グローバル設定に、任意の `executor`（実行コマンドテンプレート）を保持できるフィールドを予約する。
  - 実行結果（終了コード、ログ、実行時間）を記録できるデータ構造を用意する。
  - v0.1 では executor フィールドは保持・受け渡しのみ行い、自動起動ロジックは実装しない（インターフェースのみ提供）。

### 5.4 GitHub Issues 連携

- **対象範囲**: 設定ファイルで指定した単一リポジトリ（`owner/repo`）。
- **インポート**: GitHub Issues を取得し、タスクとして取り込む。
  - マッピング対象: タイトル、本文、ラベル、担当者、状態（open/closed）、作成・更新日時、Issue 番号・URL。
  - 既存タスクとの重複（同一 Issue から再インポート）は Issue 番号をキーに検出し、上書き or スキップを選択できる。
- **エクスポート**: ローカルタスクを GitHub Issue として新規作成する。
  - エクスポート後、タスクは対象 Issue 番号・URL を保持し、以後は「連携済みタスク」として扱う。
  - 依存関係やゴール等、Issue に自然にマッピングできない項目は本文中に構造化コメント（例: フロントマター的な記述）として埋め込むか、ラベルで代替する。
- **同期 (Sync)**:
  - ローカルとリモートの双方の `updated_at` を比較し、差分がある場合に同期対象として検出する。
  - コンフリクト（両方が更新されている）は既定では **後勝ち (last-write-wins, updated_at 比較)** とし、`--dry-run` で適用前に差分を確認できるようにする。
  - 対話的にコンフリクトを解決する手段（TUI 上での差分表示、CLI での個別選択）を提供する。
  - 認証は `gh` CLI の既存認証（`gh auth`）に委譲することを基本とし、環境変数 `GITHUB_TOKEN` によるトークン指定もサポートする。
  - **コメント同期**: Issue 本体の項目に加え、コメントスレッドも双方向で完全同期する。
    - ローカルで追加・編集したコメントは GitHub 側に反映し、GitHub 側で追加・編集されたコメントもローカルに反映する。
    - 同期はコメント単位で行い、`github_comment_id` をキーに対応付ける。ローカルのみに存在するコメント（`github_comment_id` が null）は新規作成として扱う。
    - 双方で同一コメントが編集されている場合は Issue 本体と同様に `updated_at` を比較した **後勝ち** を既定とする。
    - **削除同期**: 片方でコメントが削除された場合、もう片方にも削除を反映する（双方向）。
      - 削除は編集より優先する（**delete-wins**）: 同一コメントが片方で削除・もう片方で編集された場合、削除を正としてもう片方にも削除を反映する（編集内容は破棄される）。これは削除と編集の因果関係を判定する手段がない場合でも決定的に収束させるための方針。
      - ローカルの削除は即座に物理削除せず、`deleted_at`（tombstone）を立てて保持する。次回sync実行時にリモートへ削除を反映し、反映が完了した時点でローカルのレコードを完全に除去する。これにより、ツール未実行中に発生したリモート側の変更と削除の順序を取り違えない。
      - リモート側で削除された（＝以前 `github_comment_id` を持っていたコメントがAPI応答に存在しない）ことをsync時に検知した場合、ローカル側にも `deleted_at` を設定する。

### 5.5 TUI（ボード）

- カンバン形式で、ステータスをカラムとしてタスクを表示する。
- キーボード操作でタスクの選択、ステータス変更（カラム間移動）、詳細表示、編集ができる。
- 依存関係のインジケータ（ブロックされているタスクの視覚的表示、依存先/依存元の一覧）を表示する。
- ゴール単位でのフィルタ表示、ラベル・優先度によるフィルタ・ソートができる。
- 同期状態（未同期の変更があるか等）を表示する。
- CLI とデータストアを共有し、TUI での変更は即座にファイルに反映される（他プロセスからの読み取りと整合）。

#### 5.5.1 キーバインド仕様

vimライクなキーバインドを標準とする（Charm系ツールのデファクトとも親和性が高い）。

| キー | 動作 |
|---|---|
| `h` / `←`, `l` / `→` | カラム（ステータス）間でフォーカス移動 |
| `j` / `↓`, `k` / `↑` | カラム内でタスク間のフォーカス移動 |
| `Enter` | 選択タスクの詳細ビューを開く |
| `Space` | 選択タスクのステータスを右隣のカラムへ1段階進める |
| `Shift+H` / `Shift+L` | 選択タスクを左/右のカラムへ直接移動（任意ステータスへジャンプ） |
| `n` | 新規タスク作成フォームを開く |
| `e` | 選択タスクを編集（タイトル/本文/優先度/ラベル） |
| `d` | 選択タスクを削除（確認ダイアログ表示） |
| `D` | 依存関係エディタを開く（`depends_on` の追加・削除） |
| `g` | 選択タスクの依存関係グラフを表示 |
| `G` | ゴールによる絞り込みピッカーを開く |
| `f` | ラベル・優先度によるフィルタメニューを開く |
| `s` | ソート順を切替（優先度 / 更新日時 / 作成日時） |
| `/` | タスク検索（タイトル/本文の部分一致） |
| `S` | GitHub sync を実行（差分プレビュー → 確認 → 適用） |
| `i` | GitHub Issues をインポート |
| `Tab` | 詳細ビュー内でタブ切替（本文 / コメント / 依存関係） |
| `c` | 詳細ビューでコメントを追加 |
| `r` | データストアを再読み込み |
| `?` | ヘルプオーバーレイを表示 |
| `Esc` | フィルタ解除・ダイアログを閉じる |
| `q` / `Ctrl+C` | 終了 |

### 5.6 CLI インターフェース

エージェントからの利用を主眼に、人間可読出力と `--output json` 等による機械可読出力の両方をサポートする。想定コマンド例（最終的なコマンド名・フラグ体系は実装時に確定するが、以下の機能を満たすこと）:

| コマンド | 概要 |
|---|---|
| `init` | カレントディレクトリ/リポジトリにタスクストアを初期化する。 |
| `task add` | タスクを作成する。 |
| `task list` | タスク一覧を取得する（フィルタ: ステータス、ラベル、ゴール等）。 |
| `task show <id>` | タスク詳細を表示する。 |
| `task edit <id>` | タスクを更新する。 |
| `task rm <id>` | タスクを削除する。 |
| `task status <id> <status>` | ステータスを変更する。 |
| `dep add <id> --on <id>` | 依存関係を追加する。 |
| `dep rm <id> --on <id>` | 依存関係を削除する。 |
| `goal add` / `goal list` / `goal show` | ゴールの作成・参照。 |
| `next [--goal <id>]` | 次に実行すべき Ready タスクを取得する（機械可読出力対応）。 |
| `complete <id>` | タスクを完了として報告する。 |
| `github import` | GitHub Issues をインポートする。 |
| `github export <id>` | タスクを GitHub Issue としてエクスポートする。 |
| `github sync` | 双方向同期を実行する（`--dry-run` 対応）。 |
| `board` | TUI を起動する。 |

- すべての変更系コマンドは非対話的に実行できること（エージェントからのスクリプト実行を想定）。
- エラーは終了コードと構造化エラーメッセージ（JSON 出力時）で判別可能にする。

## 6. データモデル

タスクは GitHub Issue に準じた項目を基本としつつ、依存関係・実行メタデータ・同期メタデータを追加する。

**ID仕様**: タスクIDは `atm-` プレフィックス + UUIDv8（RFC 9562）とする（例: `atm-018f4c2e-6b8b-8b3e-9c1a-2f6b6a6f6b6a`）。`atm` はツール名 `atama` の略称。単一マシン前提のMVPでは連番より衝突リスクがない点、また文字列ソートだけで生成時刻順に並ぶ点がULID/連番に対する利点。

UUIDv8 のビットレイアウトは以下の通り確定する（UUIDv7の構造を踏襲しつつ version フィールドのみ vendor-specific な 8 を使用）:

| ビット範囲 | ビット数 | 内容 |
|---|---|---|
| 0–47 | 48 | 生成時刻のUnixミリ秒（unsigned, big-endian） — 文字列比較だけで生成時刻順ソートが可能 |
| 48–51 | 4 | version固定値 `1000`（8） |
| 52–63 | 12 | 同一ミリ秒内衝突回避用のランダム値 |
| 64–65 | 2 | variant固定値 `10`（RFC 9562準拠） |
| 66–127 | 62 | 暗号学的乱数（`crypto/rand`） |

```yaml
id: "atm-018f4c2e-6b8b-8b3e-9c1a-2f6b6a6f6b6a"   # atm- プレフィックス + UUIDv8
title: "string"
body: "markdown string"
status: "backlog|ready|in_progress|blocked|in_review|done|cancelled"   # 遷移は自由（制約なし。§5.1参照）
priority: "low|medium|high|urgent"   # 固定enum
labels: ["string"]            # 自由記述文字列
assignees: ["string"]        # 任意。人間 or エージェント識別子
depends_on: ["atm-<uuid>"]    # このタスクが依存するタスクID
goal_ids: ["atm-g-<uuid>"]    # 所属ゴール（複数ゴールへの所属を許容）
created_at: "RFC3339"
updated_at: "RFC3339"
closed_at: "RFC3339 | null"

github:                      # GitHub連携済みの場合のみ
  repo: "owner/repo"
  issue_number: 123
  url: "https://github.com/owner/repo/issues/123"
  synced_at: "RFC3339"
  remote_updated_at: "RFC3339"

comments:                     # GitHub Issueコメントとの双方向同期対象（§5.4参照）
  - id: "atm-c-<uuid>"         # ローカル採番のコメントID
    github_comment_id: "int | null"
    author: "string"
    body: "markdown string"
    created_at: "RFC3339"
    updated_at: "RFC3339"
    synced_at: "RFC3339 | null"
    deleted_at: "RFC3339 | null"   # tombstone。sync完了後に物理削除される

execution:                   # 将来の実行フック拡張のための予約領域
  executor: "string | null"  # v0.1では保持のみ。自動起動はしない
  last_run:
    started_at: "RFC3339 | null"
    finished_at: "RFC3339 | null"
    exit_code: "int | null"
    log_path: "string | null"
```

ゴール:

```yaml
id: "atm-g-018f4c2e-6b8b-8b3e-9c1a-2f6b6a6f6b6a"   # atm-g- プレフィックス + UUIDv8
name: "string"
description: "markdown string"
task_ids: ["atm-<uuid>", "atm-<uuid>"]
created_at: "RFC3339"
updated_at: "RFC3339"
```

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 実装言語 | Go。単一の静的バイナリとして配布できること。 |
| ストレージ | ローカルファイル（YAML または JSON）。**Git 管理を前提**とし、diff/レビューしやすい構造（タスク単位でのファイル分割を基本とする）とする。 |
| 起動速度 | CLI 単発コマンドは体感遅延がない程度（目安: 100ms オーダー）で応答すること。 |
| オフライン動作 | GitHub 連携コマンド以外はネットワーク接続なしで動作すること。 |
| 同時アクセス | 同一ディレクトリに対する複数プロセス（複数エージェント、TUIと同時実行等）からの読み書きに対し、ファイルロック等でデータ破損を防止すること。 |
| 可搬性 | macOS / Linux で動作すること（Windows は将来検討）。 |
| スキーマ変更耐性 | データフォーマットにバージョンフィールドを持ち、将来のマイグレーションに対応できること。 |
| セキュリティ | GitHub トークン等の認証情報を平文でリポジトリにコミットしない設計とする（`gh` CLI 委譲を推奨、トークンは環境変数経由）。 |

## 8. アーキテクチャ方針（要件レベルの制約）

### 8.1 パッケージ構成の方針

- タスクストア（永続化）、依存関係解決ロジック、GitHub 連携、CLI、TUI を疎結合なレイヤーに分離し、それぞれ単体でテスト可能にする。
- 依存関係解決やステータス管理などのコアロジックは CLI/TUI/GitHub 連携のいずれからも共通利用できるライブラリとして実装する。

### 8.2 実行委譲インターフェース

- `next` コマンドはタスクの内容に加え、そのタスクを完了させるために必要な情報（依存関係、関連 Issue、実行メタデータ）を機械可読形式で返す。
- エージェント側の実行ループは「`next` → 実行 → `complete`/`fail`」という単純なプロトコルで完結できること。

### 8.3 将来の実行フック拡張への配慮

- v0.1 では実装しないが、以下を見据えてインターフェースを予約する。
  - タスク/ゴール/グローバル設定に `executor` 定義を持たせられる。
  - 将来、`goal run --auto` のようなコマンドで `executor` を起動し、結果を自動的に `complete`/`fail` に反映できるようにする拡張ポイントを残す。

### 8.4 チーム共有への配慮（非スコープだが設計に影響する制約）

- v0.1 はローカル完結だが、将来のチーム共有（サーバー化、DB共有）を見据え、データアクセス層を抽象化しておき、将来的にストレージバックエンドを差し替え可能な設計とする。

### 8.5 使用ライブラリ方針

| 領域 | 採用ライブラリ | 理由 |
|---|---|---|
| TUIフレームワーク | `charmbracelet/bubbletea` | Elm Architecture ベースで状態管理が明確。Goの TUI 実装事実上の標準。 |
| TUIコンポーネント | `charmbracelet/bubbles` | list / viewport / textarea / help 等の既製コンポーネントで開発コストを抑える。 |
| スタイリング | `charmbracelet/lipgloss` | カラム・カード・ボーダー等のレイアウトとテーマ切替（ライト/ダーク端末対応）。 |
| Markdown描画 | `charmbracelet/glamour` | タスク本文・コメントのMarkdownをTUI上で整形表示する。 |
| CLIフレームワーク | `spf13/cobra`（想定） | サブコマンド体系（`task`, `dep`, `goal`, `github` 等）とJSON出力フラグの実装に適する。 |
| GitHub API | `go-github`（`google/go-github`）+ `gh` CLI認証委譲 | Issue/コメントCRUDを型安全に扱う。認証は §5.4 の方針に従う。 |
| UUIDv8生成 | 標準の `crypto/rand` を用いた自前実装（§6のビットレイアウトに従う） | 既存UUIDライブラリはUUIDv8のvendor-specificビットレイアウトを規定しないため、自前実装で完全に制御する。 |

## 9. 受け入れ基準（MVPの完了条件）

- [ ] タスクの CRUD、ステータス変更、依存関係の追加・削除が CLI から可能。
- [ ] 循環依存が検出・拒否される。
- [ ] ゴールに対して Ready なタスクを依存順に取得できる（`next` コマンド）。
- [ ] エージェントが `next` → 完了報告 のループでゴールを最後まで進行できることを実演できる。
- [ ] GitHub Issues のインポート・エクスポート・双方向同期（`--dry-run` 含む）が動作する。
- [ ] Issue のコメントスレッドが双方向で完全同期される。
- [ ] TUI でボード表示・ステータス変更・依存関係の可視化ができる。
- [ ] タスクデータが Git 管理下で意味のある diff を生む形式で保存される。

## 10. 決定事項

| 論点 | 決定内容 |
|---|---|
| タスク/ゴールID採番方式 | `atm-` プレフィックス + UUIDv8（RFC 9562）。タスクは `atm-<uuid>`、ゴールは `atm-g-<uuid>`（§6）。ビットレイアウトも確定済み（§6表）。 |
| ステータス遷移のバリデーション | 自由遷移。制約は設けない（§5.1）。 |
| ラベル・優先度の値域 | 優先度（priority）は固定enum、ラベル（labels）は自由記述（§6）。 |
| GitHub Issueコメントの同期 | 双方向で完全同期する。編集は本体項目と同様にlast-write-wins、削除は編集より優先（delete-wins）（§5.4）。 |
| コメント削除の伝搬方式 | tombstone（`deleted_at`）で保持し、リモートへの反映完了後に物理削除（§5.4）。 |
| ゴールをまたぐタスクの共有可否 | 許容する（1タスクが複数ゴールに属せる。`goal_ids` は配列）（§6）。 |
| TUIライブラリ・キーバインド | `charmbracelet/bubbletea` + `bubbles` + `lipgloss` + `glamour`。キーバインドはvimライクで確定済み（§5.5.1）。 |
| CLI/GitHub連携ライブラリ | `spf13/cobra`、`google/go-github`（§8.5）。 |

本書における設計判断はこれで一巡した。実装フェーズで新たに生じる論点（コマンドの正式なフラグ名、ファイル配置の具体パス等）は、実装時のドキュメント（ADRやコードコメント）で別途管理する。
