# dd-trace-go OTLP export → Jaeger (W3C)

A minimal setup for verifying [dd-trace-go v2](https://github.com/DataDog/dd-trace-go)'s
**OTLP export** across an HTTP → gRPC → gRPC → PostgreSQL call chain, sending
spans to **Jaeger** with **W3C** trace-context propagation.

```
client ──HTTP──▶ http-gateway ──gRPC──▶ grpc-service1 ──gRPC──▶ grpc-service2 ──SQL──▶ PostgreSQL
                 (REST → gRPC)          (order service)         (storage service)
                          │                    │                       │
                          └──────── OTLP/HTTP protobuf ────────────────┴──▶ Jaeger (:4318)
```

Every hop is instrumented, so a single request becomes one distributed trace
spanning all three services and the database query — visible in the Jaeger UI.

## How the OTLP export works (dd-trace-go v2.9+)

Setting `OTEL_TRACES_EXPORTER=otlp` switches the tracer from the Datadog native
protocol to an OTLP writer that reads:

| Env var                              | Purpose                                             |
| ------------------------------------ | --------------------------------------------------- |
| `OTEL_TRACES_EXPORTER=otlp`          | Enables OTLP export mode                             |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | Full URL, used verbatim — **must include `/v1/traces`** |
| `OTEL_EXPORTER_OTLP_TRACES_HEADERS`  | Extra headers (e.g. auth), comma-separated `k=v`    |

It sends **OTLP/HTTP with protobuf** (`Content-Type: application/x-protobuf`).
The endpoint is not path-adjusted, so point it at `http://jaeger:4318/v1/traces`.

Propagation is set to W3C only via `DD_TRACE_PROPAGATION_STYLE=tracecontext`, so
`traceparent`/`tracestate` headers carry the context across the gRPC hops.

## Layout

| Path                 | Role                                                        |
| -------------------- | ---------------------------------------------------------- |
| `cmd/http-gateway`   | REST API, forwards to grpc-service1 over gRPC              |
| `cmd/grpc-service1`  | Order service, orchestrates and calls grpc-service2        |
| `cmd/grpc-service2`  | Storage service, reads/writes PostgreSQL via `database/sql` |
| `proto/`             | Protobuf definitions (`order.v1`, `storage.v1`)           |
| `gen/`               | Code generated by `buf`                                    |
| `internal/tracing`   | Shared dd-trace-go tracer bootstrap                        |
| `db/init.sql`        | Schema + seed data                                         |

Instrumentation: `contrib/net/http/v2` (inbound HTTP),
`contrib/google.golang.org/grpc/v2` (server + client interceptors),
`contrib/database/sql/v2` (pgx driver → SQL spans).

## Prerequisites

- Go 1.25.5
- Docker + the `docker compose` plugin
- Tools are installed into `./bin` (no global installs)

## Generate proto code

```sh
make tools      # installs buf + protoc plugins into ./bin
make generate   # buf lint + buf generate -> gen/
```

## Run

```sh
make up         # docker compose up --build
```

- Gateway: <http://localhost:8080>
- Jaeger UI: <http://localhost:16686>

No `.env` is required — traces go to the bundled Jaeger.

## Try it

```sh
make smoke
# or manually:
curl -XPOST localhost:8080/orders -d '{"item":"book","quantity":3}'
curl localhost:8080/orders
curl localhost:8080/orders/1
```

Then open the Jaeger UI, pick service `http-gateway`, and open a trace. You'll
see spans from all three services plus the SQL `INSERT`/`SELECT`, chained by the
W3C context:

```
[http-gateway ] POST /orders
[http-gateway ] └─ order.v1.OrderService/CreateOrder      (gRPC client)
[grpc-service1] └─ order.v1.OrderService/CreateOrder      (gRPC server)
[grpc-service1]    └─ storage.v1.StorageService/SaveOrder  (gRPC client)
[grpc-service2]       └─ storage.v1.StorageService/SaveOrder (gRPC server)
[grpc-service2]          └─ INSERT INTO orders ...          (SQL span)
```

## Note on startup logs

At boot each service logs a one-time `WARN ... Unable to reach agent intake:
http://localhost:8126` diagnostic. This is harmless — dd-trace-go always runs a
startup connectivity check against the Datadog agent URL even in OTLP mode.
There is no agent in this stack; traces still flow to Jaeger over OTLP.

## Point at a different backend

Any OTLP/HTTP protobuf collector works. Override the endpoint (see
`.env.example`), e.g. an OpenTelemetry Collector or a vendor OTLP intake:

```sh
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://otel-collector:4318/v1/traces
```
